	•	Definition: A distributed database with eventual consistency guarantees that all replicas will converge to the same state over time, but not immediately.

	•	Eventual consistency allows temporary divergence but prioritizes high availability and low latency.

	•	Asynchronous cross-region database replication.

	•	Replication Lag:
	•	Writes in one region may take time to propagate to another region.
	•	Reads from different regions may see stale or inconsistent data.
	•	Split-Brain Scenarios:
	•	If a network partition occurs, different replicas may have conflicting writes that need conflict resolution.
	•	DR Challenges:
	•	If a primary region fails, the secondary region might be behind, leading to data loss or inconsistencies when failing over.
	•	Read-after-write inconsistency: A user writes data in one region but reads outdated data from another.

	•	Application Design Considerations:
	•	Use conflict resolution mechanisms (e.g., timestamp-based, last-writer-wins, vector clocks).

	•	Choose active-active or active-passive replication based on business requirements for consistency vs. availability.
	•	If strong consistency is needed, use synchronous replication, but at the cost of higher latency and lower availability.
	•	Failover Strategies:
	•	Ensure data reconciliation before failing over to a secondary region to avoid applying outdated transactions.
	•	Use quorum-based reads/writes to reduce inconsistency risks.

Brief Explanation of Network Address Translation (NAT):

Network Address Translation (NAT) is a technique used in networking to modify the IP address of packets as they pass through a router or firewall. It is commonly used at the edge of an enterprise network to allow private internal IP addresses to communicate with public internet resources.

Why NAT is Needed at the Public Edge of an Enterprise Network

Most enterprise networks use private IP addresses (e.g., 192.168.x.x, 10.x.x.x), which are not routable on the public internet. NAT allows multiple internal devices to share a single public IP address when accessing external services. This helps:
	•	Conserve IPv4 addresses, since only one public IP is needed for many internal devices.
	•	Improve security by hiding internal IP structures from the internet.
	•	Enable outbound internet access while keeping internal devices in a private network.

Scenario: NAT Between Private Networks in an Enterprise

Imagine Company A and Company B merge, but both companies have an internal network using the same private IP range (10.1.0.0/16). Directly connecting these networks would cause IP conflicts.

To resolve this:
	•	NAT can be used to translate Company A’s 10.1.0.0/16 into 192.168.10.0/24 before sending traffic to Company B.
	•	This allows seamless communication between the two networks without requiring a full re-IP of one company’s network.

Key Takeaways:
	•	NAT allows private networks to access the public internet using a single public IP.
	•	NAT can also be used inside enterprises to resolve IP conflicts when connecting private networks.
	•	It enhances security by hiding internal network structures from external entities.

	•	Example: In 192.168.1.0/24, 192.168.1.255 is the broadcast address.

2. Default Gateway Address
	•	Typically the first or last usable IP in a subnet (e.g., 192.168.1.1 or 192.168.1.254).
	•	Used by hosts to communicate with other networks via a router.
	•	Conventionally, enterprises use the first usable address (x.x.x.1), but some use the last (x.x.x.254).

3. Reserved IPs for Services (Optional but Common Conventions)
	•	Time Synchronization (NTP Servers):
	•	Some networks reserve x.x.x.2 or x.x.x.3 for internal NTP (Network Time Protocol) servers.
	•	DHCP Server Reservations:
	•	DHCP servers often reserve a range of static addresses (e.g., x.x.x.10 to x.x.x.20) for networking equipment.
	•	Infrastructure IPs (DNS, Proxy, Logging Servers):
	•	DNS Servers: x.x.x.2 or x.x.x.3 in small networks.
	•	Syslog/Monitoring: Reserved in the higher range (e.g., x.x.x.250+) for logging and SNMP systems.
	•	Virtual IPs (VIPs) for Load Balancers:
	•	Reserved within a subnet for high availability (HA) or load balancing.

Key Takeaways:
	•	Network and broadcast addresses are reserved by default and cannot be assigned to hosts.
	•	Default gateways are conventionally assigned to x.x.x.1 or x.x.x.254.
	•	Certain addresses may be reserved for services like NTP, DNS, and DHCP to maintain standardization.
	•	Consistent IP reservations ensure reliability, prevent conflicts, and improve troubleshooting efficiency.

Question:

What are some factors that influence Recovery Time Objective (RTO) and Recovery Point Objective (RPO) in disaster recovery planning?

Plausible Answers:
	•	Business Criticality of Applications:
	•	Mission-critical systems (e.g., financial transactions, healthcare systems) require low RTO/RPO, while non-essential workloads (e.g., internal reporting systems) may tolerate higher RTO/RPO.
	•	Data Change Rate & Transaction Frequency:
	•	High-frequency data changes (e.g., stock trading systems) demand low RPO to minimize data loss.
	•	Less frequently updated systems (e.g., static content servers) can tolerate higher RPO.
	•	Infrastructure & Backup Strategy:
	•	Synchronous replication supports near-zero RPO, while asynchronous replication or periodic backups result in higher RPO.
	•	Hot standby environments enable faster recovery (low RTO), whereas cold standby setups require more time to restore.
	•	Budget & Cost Constraints:
	•	Lower RTO and RPO require high-availability architectures, which increase costs due to redundancy and real-time replication.
	•	Organizations must balance cost vs. risk when defining RTO/RPO requirements.
	•	Compliance & Regulatory Requirements:
	•	Regulated industries (e.g., finance, healthcare) often mandate strict RTO/RPO to comply with disaster recovery regulations.
