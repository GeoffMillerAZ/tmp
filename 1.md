    - Leverage hybrid cloud solutions (e.g., Azure Arc, AWS Outposts, Google Anthos) to extend cloud services into the private datacenter.

Question:

In the following Terraform code snippet for Azure, a resource is misused where a data source should have been used (or vice versa).

# Attempting to pull the ID of an existing Azure Resource Group to use in a new storage account

resource "azurerm_resource_group" "existing_rg" {
  name     = "existing-resource-group"
  location = "eastus"
}

resource "azurerm_storage_account" "example" {
  name                     = "examplestorageacct"
  resource_group_name      = azurerm_resource_group.existing_rg.name
  location                 = azurerm_resource_group.existing_rg.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
}

Question:
	1.	What is wrong with the use of azurerm_resource_group in this scenario?
	2.	Should it be a resource or a data source? Why?
	3.	How would you correct the code to properly reference the ID of the existing Azure Resource Group without attempting to recreate it?
	4.	Can you explain the difference between Terraform data sources and managed resources, and when to use each?

Plausible Answers:
- What’s Wrong:
- azurerm_resource_group is incorrectly used as a resource, which tells Terraform to create or manage the resource. In this case, since the resource group already exists, Terraform will try to recreate it, leading to errors or conflicts.
- Correct Approach:
- It should use a data source to read the existing resource group without managing it:

data "azurerm_resource_group" "existing_rg" {
  name = "existing-resource-group"
}

resource "azurerm_storage_account" "example" {
  name                     = "examplestorageacct"

  location                 = data.azurerm_resource_group.existing_rg.location

  account_replication_type = "LRS"

- Resources (resource) are managed by Terraform. Terraform will create, update, or delete them based on the configuration.
- Data Sources (data) are read-only lookups that allow Terraform to reference existing resources not managed by the current Terraform configuration.
- Use a resource when you want Terraform to manage infrastructure, and a data source when you want to pull in external resources for reference.

  location = "eastus"
}

	1.	In this example, how does Terraform determine the apply order for these resources without an explicit depends_on?

	3.	Can you provide a scenario where depends_on would be required to enforce the correct apply order?

Plausible Answers:
    - How Terraform Determines Apply Order:
    - Terraform automatically infers dependencies when one resource references attributes of another.
    - In this example, since the azurerm_storage_account references azurerm_resource_group.example_rg.name and azurerm_resource_group.example_rg.location, Terraform knows it must create the resource group first before the storage account.
- Why depends_on Is Not Necessary:
    - Since there is a direct reference in the code, Terraform can build a dependency graph and apply resources in the correct order without needing depends_on.
- When depends_on Is Required:
    - depends_on is necessary when there is no direct reference between resources, but an implicit dependency exists.
- Example: If you have a network security group (NSG) and a virtual machine, and the VM needs the NSG applied to a subnet, but there’s no direct attribute reference, you’d need depends_on to ensure the NSG is created first:

resource "azurerm_network_security_group" "example_nsg" {
  name                = "example-nsg"
  location            = "eastus"
  resource_group_name = azurerm_resource_group.example_rg.name
}

resource "azurerm_virtual_machine" "example_vm" {
  name                  = "example-vm"
  resource_group_name   = azurerm_resource_group.example_rg.name
  location              = azurerm_resource_group.example_rg.location

  depends_on = [azurerm_network_security_group.example_nsg]
}

    - On the second apply, the storage account had already been successfully created during the first apply (despite the failure in the dependent resource).
